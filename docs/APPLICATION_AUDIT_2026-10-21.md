## Высокий приоритет: реальные операции и достоверность истории

### 1. Отмена одиночной операции использует переданную старую запись

**Подтверждено кодом; на устройстве не воспроизводилось.**

[BudgetDao.kt:629](M:/MyBudget/app/src/main/kotlin/ru/mybudget/app/data/BudgetDao.kt:629) сначала возвращает деньги по объекту из интерфейса, затем удаляет строку по ID. Актуальная строка не перечитывается. Повторная отмена того же объекта снова изменит баланс, даже если строки уже нет. Если операцию успели отредактировать, отменится старая сумма. Транзакция Room сама по себе не исправляет эту логическую ошибку.

**Исправление:** отменять по ID; внутри одной транзакции перечитывать строку; отсутствующая строка означает отсутствие действия. Возвращать результат выполнения. Проверить два быстрых подтверждения и отмену после редактирования.

### 2. Отмена расхода не отменяет статус оплаты обязательства/авто

**Подтверждено кодом; сквозная проверка на устройстве нужна.**

[PaymentExecution.kt:20](M:/MyBudget/app/src/main/kotlin/ru/mybudget/app/PaymentExecution.kt:20) записывает расход и отдельный маркер оплаченного периода. Между маркером и операцией нет сохраняемой связи по ID. Отмена расхода в истории не удаляет маркер и не возвращает расписание. Для авто [AutoRepository.kt:31](M:/MyBudget/app/src/main/kotlin/ru/mybudget/app/data/AutoRepository.kt:31) читает сумму/статус из журнала: исправление или отмена связанной операции в истории не обновляет журнал. В результате деньги возвращены, а событие продолжает считаться оплаченным; суммы общей и автомобильной статистики могут разойтись.

**Исправление:** единый механизм отмены связанных операций и сохранённая связь с реальным платежом. Отдельно хранить «выполнено без списания», чтобы этот статус не смешивался с оплатой из бюджета. Для авто выбрать одно правило: синхронизировать правки в обоих направлениях либо направлять редактирование в экран события.

### 3. Архивация статьи убирает её старые операции из части отчётов

**Подтверждено кодом.**

[BudgetDao.kt:171](M:/MyBudget/app/src/main/kotlin/ru/mybudget/app/data/BudgetDao.kt:171) возвращает в основной список только активные категории. [StatisticsActivity.kt:330](M:/MyBudget/app/src/main/kotlin/ru/mybudget/app/StatisticsActivity.kt:330) использует этот список как перечень допустимых ID операций. Аналогичный подход есть в годовом бюджетировании. Денежные строки остаются в базе, но выпадают из расчёта. Годовой обзор, который суммирует все операции, может показывать другую сумму.

**Исправление:** история должна включать архивные статьи; активность управляет выбором для новых операций, а не наличием прошлого факта. Хранить/показывать архивное название и бюджет статьи.

### 4. Переводы проверяют доступные деньги вне транзакции

**Риск по коду; конкурентный сценарий не запускался.**

[BudgetManager.kt:415](M:/MyBudget/app/src/main/kotlin/ru/mybudget/app/BudgetManager.kt:415) проверяет кэшированный остаток, затем вызывает отдельную денежную операцию. Два параллельных перевода могут оба пройти проверку старого остатка. Распределение по нескольким получателям выполняется серией отдельных транзакций [BudgetManager.kt:450](M:/MyBudget/app/src/main/kotlin/ru/mybudget/app/BudgetManager.kt:450), поэтому возможен частичный результат при ошибке посередине.

**Исправление:** актуальный остаток, проверка всех получателей и все изменения — в одной транзакции. Запрос должен иметь защиту от повторного выполнения.

## Статистика

### 5. Исторический график баланса рассчитывается от текущего остатка

**Воспроизведено отдельными тестами.**

[StatisticsChartHelper.kt:40](M:/MyBudget/app/src/main/kotlin/ru/mybudget/app/StatisticsChartHelper.kt:40) берёт текущий баланс и вычитает оборот только выбранного диапазона. Операции после конца исторического диапазона не исключаются. «На начало» берётся после операций первого дня [StatisticsChartHelper.kt:56](M:/MyBudget/app/src/main/kotlin/ru/mybudget/app/StatisticsChartHelper.kt:56).

Дополнительно: в режиме всех бюджетов [StatisticsActivity.kt:344](M:/MyBudget/app/src/main/kotlin/ru/mybudget/app/StatisticsActivity.kt:344) суммируются только снимки, имеющиеся в конкретный день. Если один бюджет в этот день не менялся, его остаток может отсутствовать в сумме. Переводы между бюджетами меняют их остатки без обычных income/expense, поэтому одной обратной суммы таких операций недостаточно для восстановления истории.

**Исправление:** определить достоверную модель исторического остатка: начальный баланс + полный журнал изменений либо полные согласованные снимки. Для нескольких бюджетов переносить последнее известное состояние каждого бюджета. Не показывать восстановленное значение как точное при нехватке данных.

**Исправление:** единый LocalDate в выбранном часовом поясе для операций, графиков и снимков. Проверить полночь, границу месяца и смену часового пояса.

**Исправление:** явно различать «нет настройки», «включено», «отключено». Не заменять явное отключение резервной формулой. Отдельно согласовать: отключение строки плана не должно автоматически отменять реальное обязательство — его можно показывать отдельно как конфликт настройки.

Доходы и расходы до конца текущего месяца выпадают. «Баланс на конец» может быть неверен на всю оставшуюся часть текущего месяца.

**Рекомендация:** разделить общий денежный остаток, зарезервированную часть и доступную сумму. Начинать прогноз с сегодняшнего дня либо предварительно рассчитывать конец текущего месяца. Чётко отделить резервирование от внешнего расхода.

## Импорт и резервные копии

### 17. Импорт не изолирован по бюджету и может отбрасывать реальные одинаковые операции

**Подтверждено кодом.**

## План исправления

1. **Целостность денег.** Повторная/устаревшая отмена, связанные платежи, атомарность переводов. Проверки Room: повторный запрос, два параллельных запроса, ошибка посередине, отмена после редактирования.
2. **Единые данные аналитики.** Общие правила бюджета, архивных статей, временных границ `[начало, конец)`, локальной даты и идентификаторов. После этого — исторический баланс, сводная статистика и импорт.
3. **Бюджетирование.** Семантика отсутствующего/отключённого плана, безопасный редактор, явное закрытие месяца, отсутствие изменений данных при обычном просмотре.
4. **Прогноз.** Месячные поправки доходов, остаток текущего месяца, накопление целей без повторного счёта. Согласовать общий баланс, свободные деньги и резервы. Исправить сравнение с фактом.
5. **Устойчивость и обмен.** Гонки загрузок, снимки прогнозов, CSV, предпросмотр импорта и безопасная ротация копий.
6. **Регрессионная проверка.** Сделать обычные тесты зелёными; перенести воспроизводящие сценарии аудита в постоянные тесты вместе с исправлениями. Затем отдельный запуск тестов Android и ручная проверка ключевых экранов в двух темах, двух бюджетах, на границе месяца, с архивными статьями и частичными поступлениями. APK и установка — отдельным согласованным действием.

Критерий готовности: одинаковые исходные данные дают согласованные суммы в бюджете, статистике, бюджетировании, прогнозе и выгрузках; повторная команда не меняет баланс второй раз; отмена восстанавливает и деньги, и связанные статусы.

## Идеи развития после исправлений

- **Расшифровка каждой суммы:** нажать на план/прогноз и увидеть источники, месячные поправки, реальные операции и формулу. Пометка «расчёт по неполным данным» при короткой истории.
- **Прогноз нехватки денег по датам:** не только итог месяца, но и минимальный остаток до зарплаты, день возможного дефицита и платежи, которые его создают.
- **План / факт / резерв:** разные показатели для ожидаемого дохода, полученного дохода, обязательств, отложенных средств и доступного остатка.
- **Сверка с банковской выпиской:** сначала предпросмотр и сопоставление с существующими операциями, затем подтверждение; без молчаливого удаления возможных совпадений.
- **Сценарии прогноза:** задержка зарплаты, изменение суммы премии, рост расходов, крупная покупка. Каждое изменение с понятным влиянием на будущий свободный остаток.
- **Авто:** стоимость километра и владения, расходы по месяцам/машинам, интервалы ТО. Расход топлива считать с учётом полных/неполных заправок, чтобы не показывать ложную точность.

Сейчас выгоднее укрепить общую финансовую модель и расчёты, чем добавлять новые графики поверх расходящихся данных.
